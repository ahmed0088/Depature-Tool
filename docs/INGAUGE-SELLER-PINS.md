# Fixed seller choices in IN-Gauge automation (v586)

Open a package through **Find a sale** or **Review & fix**, choose **Credit to**, check **Keep this seller fixed**, then **Save & select**. The control sits immediately below the contributor selector. Uncheck it and save to unfreeze. The choice applies to that confirmation and package family, including daily rows; it is not a default for every sale of a product or a global Opera login alias.

The existing shared Package Audit pin store is reused. The original hotel's pins remain at `pkgPins/<confirmation|family>`. Independent IN-Gauge hotels use `ingauge/targets/<identity hash>/auditContext/pins/<key>`. Choices record the contributor ID, displayed name, confirmation, product ID/name, target identity, manager and date. Target identity uses the normalized portal plus tenant/property/department IDs, independently of display labels. A renamed product can retain its choice through its saved product ID. Existing manual-sale markers survive unfreezing.

The browser validates financial fields first, then saves a single pin with a compare-and-set transaction. It keeps a read listener during that transaction, disables speculative local events, and never replaces the whole shared pin map. Another person's newer decision aborts the save and asks for a fresh review. Save controls are locked during the write, and a hotel/session change prevents installation into the wrong local context. Cancel without saving writes nothing. A changed pin on an otherwise unchanged existing sale saves only the rule and queues no financial edit.

Normal Package Audit and independent target computation use the same pin semantics. New ID-based choices compare the actual contributor ID, so two identical names or a renamed person cannot transfer ownership. An unavailable saved ID requires review; the engine does not substitute a similarly named contributor. Manual additions keep their pending status and assignment review. Explicit pins can outrank note-based seller suggestions for that package; evidence and the reason remain visible.

Reviewed operations carry a compact fixed-seller reference. The core rejects an operation whose contributor differs from that reference. The cloud runner reads the correct private pin store and rechecks a fixed reference before preflight and again before sending. Changed, removed, ambiguous or unavailable owners are held without a financial request. Denials/removals keep their existing permissions and reasoning checks. Pin metadata is not added to the IN-Gauge financial payload, and it cannot change hotel, amount, dates, product selection, approval permissions or duplicate/period checks.

Tests: `tests/ingauge-seller-pins.test.js` covers exact IDs, duplicate/renamed people, target isolation, manual-marker preservation, product renames, existing audit integration and cloud conflict holds before sending. `tests/ingauge-seller-pins.browser.test.js` covers phone/desktop contributor selection, cancel, reopen, per-entry writes, no-op saves, unfreeze, concurrent decisions, save failures, another target in the same space, manual suggestions and no global aliases. All account and financial writes in tests are synthetic.
